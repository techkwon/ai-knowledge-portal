LLM이 만든 웹앱 확장: API 키 대신 좁은 기능 권한 주기

사용자별 코드를 실행하는 앱은 작은 확장점, 실행 격리, 자원 상한과 capability 기반 접근을 함께 설계한다.

#샌드박스#권한설계#바이브코딩#웹앱

무엇을 할 수 있나요?

원저자 Jeremy Morrell은 LLM으로 개인별 작은 소프트웨어를 만들기 쉬워졌어도 배포·보안·공유는 별도 문제라고 설명한다. 웹앱의 안정된 핵심은 유지하고 이벤트·명령 같은 작은 확장점을 열어 주면 개인 기능을 추가할 때 제품 전체를 복잡하게 만들지 않을 수 있다.

설계 순서는 먼저 허용할 입력·출력과 동작을 정하고, 사용자 코드를 격리한 뒤 CPU·메모리·네트워크 요청·응답 크기·로그량에 상한을 두는 것이다. 실행 시간과 비용, 사용자가 멈춘 작업, 실패 기록도 관찰할 수 있어야 한다. 격리는 코드의 오류가 다른 사용자에게 번지는 장애 격리와 악성 코드가 데이터를 들여다보지 못하는 보안 격리를 함께 뜻한다.

예를 들어 특정 이메일 한 건을 요약하는 확장에는 전체 메일함 API 키를 넘기는 대신 이미 승인한 메일 한 건을 가져오는 함수만 전달한다. 주변의 파일·환경변수·네트워크 권한이 기본으로 열려 있지 않아야 이 좁은 capability가 실제 경계가 된다. 임의 외부 요청이나 광범위한 토큰을 남겨 둔 채 함수만 작게 만드는 것은 같은 보호가 아니다.

프록시는 실제 비밀키를 숨기고 목적지·요청 빈도를 제한하는 데 유용하지만 복잡한 API 전체를 완벽히 필터링하기는 어렵다. 원문은 넓은 권한을 준 뒤 차단 규칙을 쌓기보다 필요한 동작만 처음부터 노출하는 방식을 권한다. 인터프리터·V8 isolate·microVM·WASM/WASI 중 선택할 때는 콜드스타트·메모리·필요한 실행기능과 격리 경계를 비교한다.

운영 전 검토 예로 무한루프, 과도한 로그, 허용하지 않은 목적지로의 전송, 다른 사용자 데이터 접근을 막도록 설계 조건을 정리할 수 있다. 단순한 플랫폼 선택만으로 이 조건들이 자동 충족되는 것은 아니며, 실제 배포에서는 권한 검토와 검증이 필요하다.

살펴볼 점
  • 직접 테스트하지 않았음. 샌드박스·프록시·Cloudflare 서비스 배포나 코드 실행을 하지 않았으며 보안성을 보증하지 않는다.
  • 원문 저자는 Cloudflare 재직과 해당 기술에 대한 관점을 공개한다. 특정 벤더가 중립적으로 유일한 정답이라는 뜻으로 소개하지 않는다.
  • 공개 글의 개념을 한국어로 독립 요약하고 원문에 연결했다. 본문·코드·이미지의 재배포 라이선스는 확인되지 않아 이를 전재하거나 재사용 허가를 주장하지 않는다.
  • 클라이언트 UI에서 사용자 코드가 민감정보에 접근하는 문제는 원문도 별도 범위로 남긴다. 서버 격리만으로 모든 웹앱 위험을 해결했다고 보면 안 된다.
