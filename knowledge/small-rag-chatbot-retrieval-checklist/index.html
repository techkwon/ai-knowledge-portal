작은 RAG 챗봇 설계 점검표: 청크 크기·BM25·재순위화

학교·팀 단위 문서 챗봇을 만들 때 문서 전체를 프롬프트에 넣을 수 있는지 보고, 넘치면 청크 크기·키워드 검색·재순위화를 실험하는 설계 흐름을 Anthropic의 검색 자료로 정리했습니다.

#RAG#재순위화#BM25#청크#프롬프트 캐싱

무엇을 할 수 있나요?

1단계: 문서 양을 잽니다. Anthropic은 지식 자료가 약 20만 토큰(약 500쪽)보다 작으면 RAG 없이 전체를 프롬프트에 넣는 방법이 가장 단순하다고 설명하고, 반복 호출 비용은 프롬프트 캐싱으로 줄일 수 있다고 안내합니다.

2단계: 넘치면 청크로 나누되 크기는 실험으로 정합니다. Anthropic은 일반적인 RAG 전처리가 문서를 보통 수백 토큰 이하 조각으로 나눈다고 설명하면서도, 청크 크기·경계·겹침이 검색 성능에 영향을 준다며 사용 사례에 맞게 조정하라고 안내합니다(자체 비용 예시는 800토큰 청크를 가정). 조각만 보면 어느 문서·시기의 내용인지 알 수 없는 문제가 생기므로, 각 조각 앞에 문서 내 위치를 설명하는 짧은 맥락을 붙이는 방식(Contextual Retrieval)을 제안합니다.

3단계: 의미 검색과 키워드 검색을 함께 씁니다. 오류 코드·고유 명칭처럼 정확히 일치해야 하는 질문은 임베딩만으로 놓칠 수 있어 BM25를 결합합니다. Anthropic 실험에서 맥락 임베딩과 맥락 BM25를 함께 쓰면 상위 20개 검색 실패율이 49% 줄었습니다.

4단계: 넓게 가져와 좁게 넘깁니다. 처음에 후보를 넉넉히(실험에서는 150개) 가져온 뒤 재순위화 모델로 상위 20개만 생성 모델에 넘기면 실패율이 67%까지 줄었고, 모델이 처리할 양이 줄어 비용과 지연도 관리하기 쉬워집니다.

살펴볼 점
  • 수치는 Anthropic이 영문 데이터셋에서 측정한 결과입니다. 한국어 학교 문서는 실제 질문 표본으로 검색 실패율을 따로 측정하세요.
  • 재순위화는 단계가 하나 늘어 지연과 비용이 생깁니다. 후보 수와 넘길 개수를 바꿔 가며 균형점을 찾으세요.
  • 청크가 작을수록 항상 좋은 것은 아닙니다. 실제 질문 표본으로 크기·경계·겹침을 바꿔 가며 검색 실패율을 비교하세요. 문서 전체 입력도 사용 모델의 문맥 한도와 비용을 먼저 확인하세요.
