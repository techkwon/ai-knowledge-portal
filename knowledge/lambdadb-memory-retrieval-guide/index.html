가이드자료 확인

지식 그래프 없이 대화 기억 구현하기: 원문 보존 + 검색 기반 메모리

긴 대화 전체를 매번 모델에 다시 넣는 대신, 원문을 그대로 저장해두고 질문마다 관련 구간만 검색·재정렬해 가져오는 방식으로 긴 기억을 저렴하고 안정적으로 유지하는 설계 패턴

#장기 기억#검색 증강#토큰 비용 절감#RAG

무엇을 할 수 있나요?

핵심 원리: 대화가 길어질수록 전체 히스토리를 매 요청에 포함시키면 토큰 비용이 늘고 응답이 느려지며, 컨텍스트 창이 가득 차기 전에도 관련 없는 내용이 섞여 모델이 중요한 사실을 덜 신뢰성 있게 활용할 수 있습니다. 이 가이드는 지식 그래프를 만들거나 생성형 LLM으로 요약·정리하는 대신, 원문 텍스트와 타임스탬프를 그대로 보존하고 질문이 들어올 때만 관련 구간을 임베딩 검색 + 재정렬로 찾아오는 방식(LambdaDB 공식 블로그의 SillyMemory 사례)을 제시합니다.

사용 절차: (1) 대화를 작은 조각(청크)으로 나누고 임베딩을 생성해 저장만 해둔다 — LLM으로 요약·엔티티 추출을 하지 않는다. (2) 새 질문이 오면 그 질문 자체를 임베딩해 키워드+의미 검색을 함께 수행하고, 재정렬(rerank) 모델로 가장 관련 있는 구간만 추려낸다. (3) 추려진 원문 구간을 토큰 예산 안에서 질문·최근 대화와 함께 답변 모델에 전달한다.

예시(공식 공개 LongMemEval 500문항 평가): 전체 히스토리를 매번 그대로 넣는 방식은 정확도 95.2%에 평균 105,183 입력 토큰이 들었고, 이 검색 기반 방식은 정확도 96.0%(480/500문항)에 평균 4,886 입력 토큰(약 95% 감소)을 기록했다고 공식 블로그가 보고합니다. 전체 히스토리 방식은 476/500문항 정답으로, 이 수치만으로 통계적 유의성이나 다른 조건에서의 우위를 판단할 수는 없습니다.

적용 조건과 한계: 공식 글 스스로도 현재 방식은 질문마다 검색을 1회만 수행하는 단일 패스이며, 여러 세션에 걸친 복잡한 추론(멀티세션 리즈닝)은 더 개선할 여지가 있다고 밝힙니다(1,000만 토큰 규모 BEAM 벤치마크에서 해당 항목 점수가 상대적으로 낮음). 비용·정확도 수치는 특정 임베딩/재정렬 모델·청크 크기·벤치마크 데이터셋 조건에서 측정된 것으로, 다른 설정에서는 달라질 수 있습니다.

살펴볼 점
  • 이 카드는 공급사(LambdaDB)가 자사 제품으로 수행한 벤치마크 결과이며, 독립 기관의 재현 검증이나 이 사이트의 직접 설치·실측이 아닙니다. "95% 토큰 절감", "96% 정확도" 등의 수치를 다른 모델·데이터에 그대로 일반화하지 마세요.
  • 핵심 아이디어(원문 보존 + 질문 시점 검색)는 LambdaDB 같은 특정 상용 서비스 없이도 일반적인 벡터DB/하이브리드 검색 조합으로 구현 가능한 설계 패턴입니다. 특정 제품 도입 여부와 이 설계 원리 자체는 구분해서 참고하세요.
  • 학생 정보나 민감한 개인 대화를 실제 서비스에 적용할 때는, 원문을 그대로 외부 벡터DB·재정렬 API로 전송하게 되므로 데이터 처리 위치·보존 기간·제3자 전송 정책을 사용하려는 서비스의 공식 문서에서 별도로 확인해야 합니다.
