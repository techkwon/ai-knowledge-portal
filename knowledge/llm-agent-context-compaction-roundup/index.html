LLM 에이전트 컨텍스트 압축(컴팩션) 최신 연구 5편 비교 가이드

컨텍스트 창이 가득 찰 때 하네스가 수행하는 '압축(compaction)'의 손실 문제를 다룬 2026년 10월 arXiv 논문 5편을 비교 정리한 국내 개발자 블로그. 저자가 TRACE 공개 코드를 직접 재현해 수치를 검증했습니다.

#컨텍스트 관리#컴팩션#에이전트 메모리#Claude Code#arXiv

무엇을 할 수 있나요?

핵심 원리: 에이전트가 긴 작업 중 컨텍스트 창이 차면 하네스(Claude Code, 오픈클로 등)가 과거 기록을 요약본으로 교체하는 '컴팩션'을 수행합니다. GitHub Copilot 95조 토큰 분석(Liu 외)에 따르면 컴팩션이 발생한 세션은 전체의 7.8%뿐이지만 전체 토큰의 44.2%를 차지합니다. 이 글은 2026년 10월 arXiv에 올라온 관련 논문 5편(TRACE, ReFold, SLA, 지속 메모리 측정, MINDSET)을 비교해 세 가지 결론을 제시합니다: ①압축 시점 예측은 아직 어렵다(최고 예측기 AUROC 0.66), ②첫 번째 압축에서 맥락 손실이 가장 크다(70% vs 이후 압축 48%), ③기록을 지우기보다 보이는 부분만 접는 방식(ReFold, SLA)이 성능 손실 없이 토큰을 크게 줄였습니다.

적용 절차: 저자는 TRACE의 공개 코퍼스(github.com/nokia-applied-research/Trace)를 직접 클론해 `python -m trace_cc.scan`을 재현했고, 공개 수치와 일치함을 확인했습니다. 재현 결과 요약본을 받은 에이전트는 Python NameError가 37→208회(5.6배), 토큰/인증 누락으로 인한 HTTP 401이 73→174회(2.4배) 늘어 '압축이 다음 호출에 필요한 변수·토큰 값을 잃어버린다'는 패턴을 확인했습니다.

실무 적용 규칙(저자 제안): (1) 압축 설정을 바꾸기 전에 압축 직후 3개 행동의 에러·재요청 횟수를 먼저 측정, (2) 운영 로그에서 첫 번째 압축을 별도로 집계(손해 비율이 70% vs 48%로 크게 다름), (3) 요약문에 변수명·토큰·페이지 번호 등 다음 호출에 필요한 값을 남기도록 설계, (4) 가능하면 기록을 지우는 대신 되돌릴 수 있는 방식(중복 표시, 턴 접기)부터 적용, (5) 지속 메모리 저장소 도입 시 자기 과제에서 켜고 끈 비교를 직접 수행.

살펴볼 점
  • 참고한 arXiv 논문 5편 모두 발표 후 며칠 안 된 프리프린트로 동료 심사를 거치지 않았습니다. 저자가 직접 재현한 것은 TRACE 논문의 공개 코퍼스 하나뿐이며, 나머지 4편(ReFold·SLA·지속 메모리 측정·MINDSET)은 코드가 비공개이거나 저장소 링크가 깨져 재현하지 못했다고 명시했습니다.
  • TRACE 분석은 모델 1종(minimax-m3, 4096토큰 창)과 AppWorld 과제에 한정되며, ReFold는 Qwen3.6 2개 모델·mini-swe-agent 조합에서만 측정된 결과라 다른 모델/환경에 그대로 일반화하기는 어렵습니다. 비용 절감 수치도 실제 청구액이 아닌 단가 가정 기반 추정치입니다.
