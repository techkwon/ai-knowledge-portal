앱 안 웹뷰 로그인·본인인증: 외부 브라우저 원칙과 실제 환경 테스트

AI로 로그인·본인확인 기능은 빨리 붙어도, 브라우저에서 되던 흐름이 앱 내부 웹뷰에서 막히는 일이 흔하다. Google 공식 정책과 IETF 표준으로 확인한 원칙과 테스트 체크리스트

#OAuth#웹뷰#Google 로그인#본인인증#테스트

무엇을 할 수 있나요?

회원가입·로그인·본인확인 연동은 공식 연동 문서를 AI 코딩 도구에 주면 비교적 쉽게 구현되지만, 실제로 시간이 드는 부분은 예외 처리와 실행 환경별 테스트라는 실무 논의를 공식 자료로 좁혀 확인해 정리했습니다. 특히 일반 웹브라우저에서 잘 되던 흐름이 앱 내부 웹뷰에 띄우면 실패할 수 있습니다.

Google 공식 발표에 따르면 2021년 9월 30일부터 임베디드 웹뷰에서의 Google OAuth 요청은 차단되며 `disallowed_useragent` 오류가 납니다. Android WebView, iOS·macOS의 WKWebView(및 구형 UIWebView)가 여기에 해당합니다. 대안은 기기의 기본 브라우저로 열거나 Android Custom Tabs, iOS SFSafariViewController를 쓰는 것이고, 앱이 실행될 플랫폼(Android·iOS·데스크톱)마다 알맞은 OAuth 클라이언트를 등록해야 합니다.

근거가 되는 IETF 표준 RFC 8252(OAuth 2.0 for Native Apps, BCP 212)는 네이티브 앱이 임베디드 user-agent로 권한 요청을 해서는 안 된다(MUST NOT)고 규정합니다. 웹뷰를 띄운 앱은 로그인 입력을 기록하거나 세션 쿠키를 복사할 수 있고, 사용자는 주소창·인증서 확인 없이 자격증명을 입력하게 되기 때문입니다.

Google은 메신저·뉴스 앱이 링크를 인앱 웹뷰로 열면 해당 웹사이트의 Google 로그인도 영향받을 수 있다고 안내합니다. 제안 체크리스트: ① 일반 브라우저·인앱 브라우저·앱 내부 웹뷰를 각각 실기기(Android·iOS)에서 테스트, ② 인증 요청 후 이탈·재시도·시간 초과 같은 예외 케이스를 AI에게 목록으로 뽑게 하고 테스트 항목으로 받기, ③ 로그인 제공자·본인확인 서비스의 공식 오류 처리 문서를 구현 전에 함께 제공하기.

살펴볼 점
  • 국내 휴대폰 본인확인 서비스의 앱 연동 방식과 요금은 제공사마다 다르며 이 카드에서 확인하지 않았습니다. 해당 서비스 공식 문서를 따르세요.
  • Google 외 로그인 제공자의 웹뷰 정책은 각 제공자 문서를 확인해야 합니다. 체크리스트는 공식 원칙에서 도출한 제안이며 실제 앱으로 검증한 결과가 아닙니다.
