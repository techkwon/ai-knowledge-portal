에이전트 출시 전: 답변보다 실제 결과를 평가하기

화면 완성이나 성공 선언과 실제 업무 완료를 분리하는 평가 설계

#실무 가이드#커뮤니티 인사이트

무엇을 할 수 있나요?

핵심 원리: 에이전트가 완료했다고 말한 기록과 실제 환경의 최종 상태는 다릅니다. 평가에는 입력·성공 기준·실행 기록·결과 확인을 함께 둡니다.

절차: 대표 업무와 알려진 실패를 테스트 사례로 만들고, 통과 조건을 먼저 적습니다. 같은 과제를 여러 번 실행해 단발성 성공과 반복 가능한 성공을 구분합니다.

예시: 문서 작성 에이전트라면 파일 존재·필수 항목·수치 일치와 원문 근거를 확인합니다. 외부 작업은 테스트 환경에서 승인·오류 처리·최종 상태를 검증합니다.

개선: 프롬프트나 도구를 바꾸기 전후에 같은 사례를 실행하고 새 실패를 회귀 평가에 추가합니다. UI 시연만으로 운영 준비 완료를 판단하지 않습니다.

업무별 평가셋을 나누면 모델 교체 판단이 더 분명해집니다. 실제 업무의 입력·기대 결과·오류를 모으고 성공 기준을 고정한 뒤, 이미 잘하는 회귀 과제와 아직 어려운 능력 과제를 구분합니다. 같은 과제를 여러 번 trial하고 합산 성공률뿐 아니라 작업 종류·난이도별 결과, 비용·토큰·지연시간을 함께 기록합니다. 예를 들어 단일 파일 수정과 여러 파일·DB가 연결된 수정을 같은 묶음의 점수 하나로만 비교하지 않는 방식입니다. 자동 채점도 사람의 표본 검토로 보정하세요.

No AI Slop 선언은 AI 사용 자체보다 결과 품질과 독자 경험에 대한 책임 없이 출력을 넘기는 것을 문제로 봅니다. 생산량보다 실제 사용과 도움을 우선하고, 작성자가 아낀 시간보다 읽는 이가 더 큰 이해 부담을 떠안는지 점검하자는 관점입니다.

공유 전에 에이전트 작성 여부를 밝히고 중요한 부분을 확인합니다. 자동 리뷰·린터·검증기는 도움이 되지만 충분하지 않으므로, 위험 수준에 맞춰 사람이 계획·설계·결과 중 검토할 범위를 명시합니다. 선언은 모든 코드를 항상 전량 읽으라고 요구하는 것으로 요약하지 않습니다.

같은 실수가 두 번 나타나면 출력만 덧대기보다 시스템과 가드레일을 개선합니다. 린터·타입 검사·자동 검사가 잡을 수 있는 반복 오류는 검사로 옮기고, 평가 지표에는 토큰·PR·에이전트 수보다 실제 배포물·사용·효용을 포함합니다.

살펴볼 점
  • 특정 사업의 개발 기간·비용·성공률을 추정한 가이드가 아닙니다. 실제 사용자 평가와 운영 모니터링도 필요합니다.
  • 평가 기록에도 개인정보가 남을 수 있습니다. 비식별 테스트 데이터와 제한된 접근 권한을 사용하세요.
  • 공식 글의 관련 평가 원리를 독립 요약한 절차입니다. 직접 평가셋을 구축하거나 모델 비교·실행을 하지 않았으며 특정 모델의 서열·성공률을 제시하지 않습니다.
  • 공개 선언의 가치·실천 원칙이지 대조 실험으로 입증된 생산성 효과나 의무적 법규가 아닙니다. 직접 평가셋 구축·실행·효과 측정은 하지 않았습니다.
  • 선언 본문을 독립 한국어 요약했습니다. 원문 재배포 라이선스는 확인하지 않았습니다. 모델 API 요금·데이터 정책·학생 이용 연령·코드 또는 가중치 라이선스를 부여하는 문서는 아닙니다.
  • 이번 보강은 No AI Slop 선언의 원칙을 추가한 범위입니다. 기존 평가 가이드의 모든 출처를 다시 검토하거나 실제 평가를 실행한 것은 아닙니다.
